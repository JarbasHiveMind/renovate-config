# AGENTS.md — `renovate-config`

Guidance for AI coding agents (and humans) working in this repository. Read it
fully before making changes. It encodes conventions that are not obvious from
the code and that, if ignored, produce work that will be rejected.

## Repo

This repository holds the shared [Renovate](https://docs.renovatebot.com/)
preset that other repos in the [HiveMind](https://github.com/JarbasHiveMind)
org pull in via `extends`. It has no application code, no build, and no
tests — a single JSON file, `org-inherited-config.json`, that centralizes
dependency-update rules org-wide instead of duplicating them per repo. Part
of the HiveMind ecosystem — a protocol for connecting satellite devices to a
hub running [OpenVoiceOS](https://github.com/OpenVoiceOS); the hub is
[HiveMind-core](https://github.com/JarbasHiveMind/HiveMind-core).

## Layout / build / test

- `org-inherited-config.json` is the entire payload: a Renovate config object
  (currently one `packageRules` entry widening the range strategy for
  `peerDependencies`). There is no `src/`, no package manifest, no test
  suite, and none should be added — this repo's only job is to be valid,
  minimal JSON that other repos reference.
- Validate a change by checking the file parses as JSON and, ideally, against
  the [Renovate config schema](https://docs.renovatebot.com/renovate-schema.json)
  before opening a PR (e.g. `python3 -m json.tool org-inherited-config.json`
  as a baseline sanity check; a schema validator is stronger if available).

## Working agreement (org-wide law)

- **Git identity is always** `JarbasAi <jarbasai@mailfence.com>`. Never set a
  per-repo override.
- **Never push `dev` or `master`.** Work on a feature branch and open a
  **draft** PR into `main`. A human merges. You do not merge your own PRs.
- **Never merge or modify `Release X → master` PRs.** They are the
  maintainer's stable-release mechanism, generated by automation.
- **One commit per PR** (squash before pushing). Conventional commits;
  `feat:` only for a user-visible new capability. `fix:`, `docs:`, `chore:`,
  `ci:` otherwise.
- **Disclose AI authorship.** Every PR/issue/comment an agent writes carries,
  at the top: `> 🤖 Auto-generated by <model> via Claude Code — NOT
  human-reviewed. Verify before acting.` PR bodies are plain human prose
  (3–6 short paragraphs), no tables or section-symbol spray.
- **Never edit someone else's** issue, PR description, or comment. Add a
  comment instead; on your own PRs, edit the body rather than piling on
  comments.
- Keep durable text (README, docs, PR bodies, comments) timeless and
  standalone: no dates, no "currently/now/new", no meta-commentary about the
  edit itself.
- No scratch files, committed virtualenvs, `__pycache__`, `.pyc`, or build
  artifacts in a PR. `git show --stat` shows only intended files.
- **Keeping this AGENTS.md current is a quality gate.** Any PR that changes
  this repo's conventions, config shape, or how it is consumed updates
  AGENTS.md in the same PR. A stale AGENTS.md is a review-blocking defect,
  the same tier as a failing test.

## Dependencies

This repo has no dependency manifest of its own — it exists to CONFIGURE how
Renovate updates dependencies in every *other* HiveMind repo. Any rule added
here must not fight the org's floor-pins-only / no-lockfile policy used
throughout HiveMind and OVOS repos: prefer rules that widen ranges or bump
floors promptly (like the existing `peerDependencies` `widen` rule), never
rules that pin exact versions, generate or commit lockfiles, or cap floors
below a package's latest alpha. Apache-2.0.

## Tests

There is no test suite; the closest thing to a regression check is: the JSON
must remain valid, and the config must not silently regress a consuming
repo's Renovate behavior (e.g. re-introduce pinning or lockfile generation).
Before merging a change, spot-check that at least one consuming repo's
`renovate.json` (`"extends": ["github>JarbasHiveMind/renovate-config"]`)
still resolves the preset as intended. CI green is permission to review, not
to merge. A non-trivial change gets an adversarial review before it lands.

## Repo-specific rules

- This is a shared config repo, not application code: a rule change here
  propagates to every org repo that extends it on the next Renovate run —
  treat edits as infrastructure changes with organization-wide blast radius,
  not local tweaks.
- Keep the config minimal and generic (`packageRules`, `extends`, and similar
  org-level knobs). Do not add repo-specific package rules here that only
  make sense for one consumer — those belong in that repo's own
  `renovate.json`, which extends this preset.
- Never add a rule that pins to an exact version, disables updates for a
  package wholesale, or generates/commits a lockfile — that would fight the
  floor-pins-only, no-lockfile, latest-alphas policy every HiveMind and OVOS
  repo follows.
- If Renovate's own schema or preset-extension syntax changes upstream, fix
  the config to match and note the reason in the PR — never guess at syntax.
